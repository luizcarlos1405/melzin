# Melzin example: member profile

A small app with two pages: the members (`/`) and a member's profile with a follow button
(`/u/:handle`). Who you are and who you're looking at decide what the profile shows. It's a separate app
that uses Melzin as a workspace package (`"melzin": "workspace:*"`), with a tiny Bun backend that owns
the people and who follows whom. It's where conditionals (`m-if`, `m-else-if`, `m-else`, `m-show`),
routing (routes.json, links, the standalone host) and lists (`m-for`) get a real screen, and the seed
of the profile page that SPEC §11 plans as the first real prototype.

## Run it

From the repo root, run `bun install` once. Then, from `examples/profile/`:

| Command | What it does |
|---|---|
| `bun run dev` | the app on http://localhost:3002 (`PORT` overrides), CSS rebuilt on every request |
| `bun run start` | the same with `NODE_ENV=production`: CSS built once, production bundle |
| `bun run shell` | the preview shell on http://127.0.0.1:4321: every snapshot of every view |
| `bun run check` | checks `views/*.mel.html` and `routes.json` (expect `0 errors, 0 warnings in 3 files`) |
| `bun run types` | regenerates `routes.types.ts` and the views' `*.types.ts` from routes.json and the schemas |
| `bun run typecheck` | `tsc --noEmit` |
| `bun test` | the contract, API, view and app tests |

There are no accounts: `?as=ana` says who is looking, on either page. Without `as`, nobody is signed in,
and "Sign in to follow" signs in as Ana. The members page links to every scenario: as Ana, Bruno's
profile can be followed back; as Bruno, Ana's already follows her; Carla's profile is empty; and Ana on
her own profile sees "This is you". In the shell, the two routes are listed as pages, and each card's
URL bar shows (and edits) the URL its snapshot stands for.

## Files

```
theme.css                 project-wide Tailwind theme (D12): a violet brand scale, page background, font
routes.json               the route table: / shows members, /u/:handle shows profile (SPEC D21)
routes.types.ts           generated by `melzin types routes.json`; don't edit
views/members.mel.html    the members: who is looking, links to try each scenario, a card per member
views/profile.mel.html    the profile: avatar, name, badges, bio, details, stats and the follow button
views/*.types.ts          generated by `melzin types`; don't edit
model.ts                  the people, the follows and the adapter, with no server in it
source.ts                 the two sources: remote (the API) and local (the adapter on the device)
server.ts                 Bun.serve: API, view files, CSS, the page for every route
index.html, client.ts     the production page: startApp with the remote source
tests/                    contract, API, view and app tests
```

## What it shows

- **Routes as a table (SPEC D21, D22).** `routes.json` names each route, its path in URLPattern syntax
  and its view. `melzin check` checks it with the views; `melzin types routes.json` generates the
  `Routes` type that the source and the href helper are typed with.
- **Links the view never builds (D23).** The member cards and the "Members" link bind `m-bind:href` to
  link fields (`"route": "profile"` in the schema). The adapter fills them with `href()` from
  `routes.json`, keeping `?as=`, and the generated `Href` type rejects a hand-built string.
- **The URL as input (D27).** The members page reads `route.query.as` for "Browsing as @ana", with no
  data field for it; its snapshots set the URL they stand for with `"route": { "query": ... }`.
- **One contract, two sources (D20).** `remoteSource()` asks the server's API; `localSource(network)`
  runs the same adapter (`model.ts`) in the browser, as an offline-first app would on top of IndexedDB.
  `client.ts` uses the remote one; `tests/app.test.ts` runs the whole app on the local one, with no
  server.
- **A list keyed by the schema (SPEC D34).** The members page is one card repeated with
  `m-for="member in members"`. `members` is a list in the schema, `"type": "array"` with
  `"key": "handle"`, so an update keeps each member's card, and moves it when someone new sorts before
  them; the markup never names the key. The adapter sends everyone, sorted by handle, so the order is
  stable. A required list is never missing, only empty: the `<ul>` shows with `m-if="members.length"`,
  and an `m-else` after it is the "No members yet" design. `melzin check` asks for snapshots of both
  list states, so "one member" and "no members yet" sit next to the full page. Lists replace whole
  when a snapshot extends another (D36): "browsing as Ana" restates all three cards to change their
  links, and "one member" extends it with a one-item list.
- **Navigation (D25).** Links between the pages switch screens without reloading, back and forward
  work, and "Sign in to follow" is a handler that navigates to the same profile as Ana. Hovering a
  card loads that profile ahead of the click (D24).

- **One action out of four, picked by data.** The follow button is an `m-if` chain on the optional
  `viewer` object: `m-if="!viewer"` (nobody signed in: "Sign in to follow"), `m-else-if="viewer.isSelf"`
  ("This is you"), `m-else-if="viewer.following"` ("Following", which unfollows) and `m-else` ("Follow",
  or "Follow back" through a nested `m-if`). Exactly one is in the document at a time, and a follow
  swaps it in place.
- **Designed fallbacks for optional fields (SPEC #9).** `bio`, `pronouns` and `location` are optional.
  The adapter leaves out what a person never filled in, and the view shows "No bio yet." through
  `m-else`, or nothing at all for pronouns and location. `m-show` handles the badges: verified and
  "Follows you".
- **Every state in a snapshot.** The snapshots are "signed out", "follows you", "following", "your own
  profile", "empty profile" and "very long everything". `melzin check` warns when no snapshot shows an
  element behind a condition, so each branch of the design gets reviewed in the shell. The long one
  found a real limit: nine-digit counts don't fit the stats row on a phone, so the adapter sends
  `98.8M` instead of `98,765,432`.
- **The adapter (P3).** `toViewModel` in `model.ts` turns stored people and follows into exactly the
  profile view's data: initials, a `Joined March 2021` label, counts formatted to fit, the viewer's
  relationship to the profile and the link back. `toMembersModel` does the same for the members page:
  everyone, by handle, each with their follower count and a link that keeps who is looking.
  `tests/contract.test.ts` checks their output against the schemas for everyone seen by everyone, and
  that each snapshot is exactly what the adapter sends for some state, at the URL it sets.
- **The view under test.** `tests/view.test.ts` mounts the real view file with the real runtime in
  happy-dom, fed by the adapter, and checks that each backend state shows the right controls and that
  they send the right events. For the members page it checks that an update keeps each card's element
  when members join or leave, and that the empty state takes the list's place.
- **Events out, typed (D14, D15).** The source's handlers are typed by the generated `Routes`, so a
  missing or misspelled handler fails `tsc`. `follow` and `unfollow` call the API, which answers with
  the profile as the viewer now sees it, and the handler passes that to `page.update`.

## API

| Route | Response |
|---|---|
| `GET /api/members` | the members page as nobody sees it, `{ "members": [...] }` with everyone by handle; `?as=<viewer>` as that viewer sees it (400 for an unknown viewer) |
| `GET /api/profiles/<handle>` | the profile as nobody sees it (`Data` in `views/profile.types.ts`); 404 for an unknown handle |
| `GET /api/profiles/<handle>?as=<viewer>` | the same, as `<viewer>` sees it; 400 for an unknown viewer |
| `PUT /api/profiles/<handle>/followers/<viewer>` | `<viewer>` follows `<handle>`; returns the profile as `<viewer>` now sees it. 400 for following yourself, 404 for unknown people |
| `DELETE /api/profiles/<handle>/followers/<viewer>` | `<viewer>` stops following `<handle>`; returns the same |
| `GET /views/<name>.mel.html` | a view file, verbatim, `Cache-Control: no-store`; anything else under `/views/` is a 404 |
| `GET /styles.css` | Tailwind for `views/` plus `theme.css` |
| `GET /` and `GET /u/<handle>` | `index.html`, with `client.ts` bundled by Bun: one entry per route in routes.json |

Follows live in memory, so restarting the server resets them. They change through PUT and DELETE,
which another site can't send without a CORS preflight that this server never answers.
