# Melzin example: member profile

A member's profile page with a follow button: who you are and who you're looking at decide what the
page shows. It's a separate app that uses Melzin as a workspace package (`"melzin": "workspace:*"`), with
a tiny Bun backend that owns the people and who follows whom. It's where conditionals (`m-if`,
`m-else-if`, `m-else`, `m-show`) get a real screen, and the seed of the profile page that SPEC §11
plans as the first real prototype.

## Run it

From the repo root, run `bun install` once. Then, from `examples/profile/`:

| Command | What it does |
|---|---|
| `bun run dev` | the app on http://localhost:3002 (`PORT` overrides), CSS rebuilt on every request |
| `bun run start` | the same with `NODE_ENV=production`: CSS built once, production bundle |
| `bun run shell` | the preview shell on http://127.0.0.1:4321: every snapshot of every view |
| `bun run check` | checks `views/*.mel.html` (expect `0 errors, 0 warnings in 2 files`) |
| `bun run types` | regenerates `views/profile.types.ts` from the profile's schema |
| `bun run typecheck` | `tsc --noEmit` |
| `bun test` | the contract test, the API tests and the view tests |

There are no accounts: `?profile=bruno` picks whose profile, and `?as=ana` who is looking. Without `as`,
nobody is signed in, and "Sign in to follow" signs in as Ana. The bar at the top links to every
scenario: Ana on Bruno's profile can follow him back, Bruno on Ana's already follows her, Carla's
profile is empty, and Ana on her own profile sees "This is you".

## Files

```
theme.css                 project-wide Tailwind theme (D12): a violet brand scale, page background, font
views/profile.mel.html    the profile: avatar, name, badges, bio, details, stats and the follow button
views/profile.types.ts    generated by `melzin types`; don't edit
views/scenarios.mel.html  a static view: links to the demo's scenarios
server.ts                 Bun.serve: API, adapter, view files, CSS, the page
index.html, client.ts     the production page
tests/                    contract.test.ts, api.test.ts and view.test.ts
```

## What it shows

- **One action out of four, picked by data.** The follow button is an `m-if` chain on the optional
  `viewer` object: `m-if="!viewer"` (nobody signed in: "Sign in to follow"), `m-else-if="viewer.isSelf"`
  ("This is you"), `m-else-if="viewer.following"` ("Following", which unfollows) and `m-else` ("Follow",
  or "Follow back" through a nested `m-if`). Exactly one is in the document at a time, and a follow
  swaps it in place.
- **Designed fallbacks for optional fields (SPEC #9).** `bio`, `pronouns` and `location` are optional.
  The adapter leaves out what a person never filled in, and the view shows "No bio yet." through
  `m-else`, or nothing at all for pronouns and location. `m-show` handles the badges: verified and
  "Follows you".
- **Every state in a snapshot.** The snapshots are "signed out", "follows you", "following", "your own
  profile", "empty profile" and "very long everything". `melzin check` warns when no snapshot shows an
  element behind a condition, so each branch of the design gets reviewed in the shell. The long one
  found a real limit: nine-digit counts don't fit the stats row on a phone, so the adapter sends
  `98.8M` instead of `98,765,432`.
- **The adapter (P3).** `toViewModel` in `server.ts` turns stored people and follows into exactly the
  profile view's data: initials, a `Joined March 2021` label, counts formatted to fit, and the viewer's
  relationship to the profile. `tests/contract.test.ts` checks its output against the schema for every
  person seen by everyone, and that each snapshot is exactly what the adapter sends for some state.
- **The view under test.** `tests/view.test.ts` mounts the real view file with the real runtime in
  happy-dom, fed by the adapter, and checks that each backend state shows the right controls and that
  they send the right events.
- **Events out, typed (D14, D15).** `client.ts` mounts the profile with the generated `Data` and
  `Handlers`, so a missing or misspelled handler fails `tsc`. `follow` and `unfollow` call the API,
  which answers with the profile as the viewer now sees it, and the client passes that to
  `view.update`.

## API

| Route | Response |
|---|---|
| `GET /api/profiles/<handle>` | the profile as nobody sees it (`Data` in `views/profile.types.ts`); 404 for an unknown handle |
| `GET /api/profiles/<handle>?as=<viewer>` | the same, as `<viewer>` sees it; 400 for an unknown viewer |
| `PUT /api/profiles/<handle>/followers/<viewer>` | `<viewer>` follows `<handle>`; returns the profile as `<viewer>` now sees it. 400 for following yourself, 404 for unknown people |
| `DELETE /api/profiles/<handle>/followers/<viewer>` | `<viewer>` stops following `<handle>`; returns the same |
| `GET /views/<name>.mel.html` | a view file, verbatim, `Cache-Control: no-store`; anything else under `/views/` is a 404 |
| `GET /styles.css` | Tailwind for `views/` plus `theme.css` |
| `GET /` | `index.html`, with `client.ts` bundled by Bun |

Follows live in memory, so restarting the server resets them. They change through PUT and DELETE,
which another site can't send without a CORS preflight that this server never answers.
