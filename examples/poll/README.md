# Melzin example: meetup poll

A quick poll, "What should we eat at the next team meetup?", with a list of options and one `vote`
event that says which option was picked. It's a separate app that uses Melzin as a workspace package
(`"melzin": "workspace:*"`) and has a tiny Bun backend that owns the votes.

## Run it

From the repo root, run `bun install` once. Then, from `examples/poll/`:

| Command | What it does |
|---|---|
| `bun run dev` | the app on http://localhost:3000 (`PORT` overrides), CSS rebuilt on every request |
| `bun run start` | the same with `NODE_ENV=production`: CSS built once, production bundle |
| `bun run shell` | the preview shell on http://127.0.0.1:4321: every snapshot of every view |
| `bun run check` | checks `views/*.mel.html` (expect `0 errors, 0 warnings in 2 files`) |
| `bun run types` | regenerates `views/poll.types.ts` from the poll's schema |
| `bun run typecheck` | `tsc --noEmit` |
| `bun test` | the contract, view and API tests |

Open the app in two tabs and vote in one: the other picks up the new counts within 3 seconds.

## Files

```
theme.css                 project-wide Tailwind theme (D12): brand colours, page background, font
views/poll.mel.html       the poll: question, one row per option with votes, percent and a Vote button
views/poll.types.ts       generated by `melzin types`; don't edit
views/header.mel.html     a static view: no schema, no data, no events
server.ts                 Bun.serve: API, adapter, view files, CSS, the page
index.html, client.ts     the production page
tests/                    contract.test.ts, view.test.ts and api.test.ts
```

## What it shows

- **The adapter (P3).** The backend defines a poll (`MEETUP_POLL` in `server.ts`: the question and its
  options, each with an `id`, a label and an emoji) and stores plain counts by option id
  (`{pizza: 3, tacos: 1, sushi: 0}`). `toViewModel` turns them into exactly what the screen shows: one
  item per option, in the poll's order rather than by votes (so a row never moves away from the
  pointer about to vote on it), with its votes and a percent string like `"75%"`, and a total label
  like `"4 votes"` or `"No votes yet"`. The view never computes anything; it only displays fields.
  `tests/contract.test.ts` loads the poll's schema with `loadViewFile` and runs `validateData` over the
  adapter's output for several states, zero votes included, so a drifted adapter fails the test (SPEC
  §9.3): an unknown field, a value of the wrong type, an option without its id, an id used twice or
  a poll with one option. It also checks that every snapshot is a state the adapter can produce.
- **A list keyed by the schema (SPEC D34).** Each option is one row repeated with
  `m-for="option in options"`. `options` is a list in the schema, `"type": "array"` with
  `"key": "id"` and `"minItems": 2` (a poll needs a choice), so an update keeps each option's row and
  button, and moves the row if the options change order; the markup never names the key. Because the
  list is never empty, `melzin check` doesn't ask for an empty state, only for a snapshot with more
  than one item. Every row is the same template, so the options' hand-drawn icons became an `emoji`
  field shown with `m-text` in one brand-tinted square (attributes can't be bound from data yet), and
  the button says "Vote" with ` for Pizza` in `sr-only` text, filled from `option.label`.
- **One event with a payload, typed (D14, D15, D35).** The view declares one `vote` event whose payload
  is `{ optionId: string }`, and each row's button emits it with
  `m-on:click="emit('vote', { optionId: option.id })"`; `melzin check` matches every emit against the
  payload. `client.ts` mounts the view with `mount<Data, Handlers>` and the generated types, so a
  missing or misspelled handler, a payload read as the wrong shape, or data of the wrong shape, fails
  `tsc`. The handler, `vote: ({ optionId }) => ...`, POSTs that same object and calls `view.update`
  with the server's answer; only the changed text is rewritten, and the rows and buttons keep their
  elements (`tests/view.test.ts` mounts the real view in happy-dom to check it).
- **The same file in production (P5).** `/views/*` serves the view files byte for byte, exactly as the
  shell does, and `/styles.css` comes from the same `buildCss` the shell uses. With the same data and
  device size, the page looks like the matching frame in the shell.
- **Snapshots (P4).** The poll has `no votes yet`, `close race`, `landslide`, `huge numbers`,
  `very long question` and `six options with long labels`, so awkward data is visible in the shell
  before it shows up in production. The last one is why a phone stacks each row's percent above its
  button: with them side by side, a long label got a column a word wide. The last two extend
  `close race` (D30). Lists replace whole when a snapshot extends another (D36), so `six options with long labels`
  states its whole list, and `very long question`, which only changes the question, keeps the base's.

## API

| Route | Response |
|---|---|
| `GET /api/poll` | the poll's view model (`Data` in `views/poll.types.ts`) |
| `POST /api/poll/votes` with `{"optionId": "pizza"}`, the view's `vote` payload | counts the vote and returns the new view model; 415 if the body isn't `application/json`, 400 with `{"error"}` for any other bad request, such as an id the poll doesn't have |
| `GET /views/<name>.mel.html` | a view file, verbatim, `Cache-Control: no-store`; anything else under `/views/` is a 404 |
| `GET /styles.css` | Tailwind for `views/` plus `theme.css` |
| `GET /` | `index.html`, with `client.ts` bundled by Bun |

Votes live in memory, so restarting the server resets the poll.
