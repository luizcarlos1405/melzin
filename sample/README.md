# Melzin sample: meetup poll

A quick poll, "What should we eat at the next team meetup?", with three fixed options. It's a separate
app that uses Melzin as a workspace package (`"melzin": "workspace:*"`) and has a tiny Bun backend that
owns the votes.

## Run it

From the repo root, run `bun install` once. Then, from `sample/`:

| Command | What it does |
|---|---|
| `bun run dev` | the app on http://localhost:3000 (`PORT` overrides), CSS rebuilt on every request |
| `bun run start` | the same with `NODE_ENV=production`: CSS built once, production bundle |
| `bun run shell` | the preview shell on http://127.0.0.1:4321: every snapshot of every view |
| `bun run check` | checks `views/*.mel.html` (expect `0 errors, 0 warnings in 2 files`) |
| `bun run types` | regenerates `views/poll.types.ts` from the poll's schema |
| `bun run typecheck` | `tsc --noEmit` |
| `bun test` | the contract test and the API tests |

Open the app in two tabs and vote in one: the other picks up the new counts within 3 seconds.

## Files

```
theme.css                 project-wide Tailwind theme (D12): brand colours, page background, font
views/poll.mel.html    the poll: question, three options with votes, percent and a Vote button
views/poll.types.ts       generated by `melzin types`; don't edit
views/header.mel.html  a static view: no schema, no data, no events
server.ts                 Bun.serve: API, adapter, view files, CSS, the page
index.html, client.ts     the production page
tests/                    contract.test.ts and api.test.ts
```

## What it shows

- **The adapter (P3).** The backend stores plain counts (`{pizza: 3, tacos: 1, sushi: 0}`).
  `toViewModel` in `server.ts` turns them into exactly what the screen shows: votes, a percent string
  like `"75%"` and a total label like `"4 votes"` or `"No votes yet"`. The view never computes anything;
  it only displays fields. `tests/contract.test.ts` loads the poll's schema with `loadViewFile` and runs
  `validateData` over the adapter's output for several states, zero votes included, so a drifted adapter
  fails the test (SPEC §9.3). It also checks that every snapshot is a state the adapter can produce.
- **Events out, typed (D14, D15).** The view declares `votePizza`, `voteTacos` and `voteSushi` and emits
  them with `m-on:click="emit('votePizza')"`. `client.ts` mounts it with `mount<Data, Handlers>` and the
  generated types, so a missing or misspelled handler, or data of the wrong shape, fails `tsc`. Each
  handler POSTs the vote and calls `view.update` with the server's answer; only the changed text is
  rewritten and the buttons keep their identity.
- **The same file in production (P5).** `/views/*` serves the view files byte for byte, exactly as the
  shell does, and `/styles.css` comes from the same `buildCss` the shell uses. With the same data and
  device size, the page looks like the matching frame in the shell.
- **Snapshots (P4).** The poll has `no votes yet`, `close race`, `landslide`, `huge numbers` and
  `very long question`, so awkward data is visible in the shell before it shows up in production.

## API

| Route | Response |
|---|---|
| `GET /api/poll` | the poll's view model (`Data` in `views/poll.types.ts`) |
| `POST /api/poll/votes` with `{"option": "pizza" \| "tacos" \| "sushi"}` | counts the vote and returns the new view model; 415 if the body isn't `application/json`, 400 with `{"error"}` for any other bad request |
| `GET /views/<name>.mel.html` | a view file, verbatim, `Cache-Control: no-store`; anything else under `/views/` is a 404 |
| `GET /styles.css` | Tailwind for `views/` plus `theme.css` |
| `GET /` | `index.html`, with `client.ts` bundled by Bun |

Votes live in memory, so restarting the server resets the poll.
